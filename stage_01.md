# 2. Назначение и границы проекта

## 2.1. Назначение системы

Разрабатываемая программная система предназначена для автоматизации учёта товаров, контроля остатков и регистрации движений материальных ценностей на складе.

Пользователь системы (кладовщик) должен иметь возможность:

- просматривать номенклатуру товаров;
- регистрировать поступление товаров (приход);
- регистрировать отгрузку товаров (расход);
- просматривать текущие остатки по складам и ячейкам;
- просматривать историю движений товаров.

Администратор системы должен иметь возможность:

- добавлять и изменять карточки товаров и категории;
- управлять справочником складов и ячеек;
- управлять справочником контрагентов;
- просматривать аналитические отчёты.

---

## 2.2. Основные объекты предметной области

В системе выделены следующие основные сущности:

- товар (номенклатура);
- категория товара;
- склад / ячейка хранения;
- остаток товара;
- документ движения (приход / расход);
- контрагент (поставщик / получатель).

Примеры товаров:

- Ноутбук Lenovo ThinkPad;
- Бумага офисная А4;
- Картридж для принтера HP.

---

## 2.3. Границы проекта

### В систему входит:

1. Ведение каталога товаров и категорий.
2. Управление структурой складов и ячеек.
3. Регистрация документов поступления (прихода).
4. Регистрация документов отгрузки (расхода).
5. Автоматический пересчёт остатков.
6. Контроль минимального остатка (базовое уведомление).
7. Просмотр истории движений и оборотной ведомости.
8. Хранение информации о контрагентах.

### В систему не входит:

В рамках курсового проекта не реализуются:

- интеграция с физическим оборудованием (ТСД, сканеры штрих-кодов);
- обмен данными с внешними ERP-системами (1С, SAP);
- автоматическое формирование заказов поставщикам;
- мобильное приложение для кладовщиков;
- расчёт логистических маршрутов;
- финансовый учёт и расчёт себестоимости.

Эти функции могут быть добавлены при дальнейшем развитии проекта.

# 4. Перечень модулей системы

В проекте выделено четыре основных функциональных модуля.

| Модуль | Ответственность |
| --- | --- |
| CatalogModule | Хранение информации о товарах, категориях и единицах измерения |
| InventoryModule | Управление складами, ячейками и учёт текущих остатков |
| MovementModule | Регистрация прихода, расхода и инвентаризации |
| CounterpartyModule | Хранение информации о поставщиках и получателях |

Дополнительно используется `ApiHost`, который принимает запросы от пользовательского интерфейса и передает их соответствующим модулям.

---

## 4.1. CatalogModule

Отвечает за номенклатуру.

Основные функции:

- получение списка товаров;
- получение информации о товаре;
- добавление и редактирование карточек товаров;
- управление категориями.

---

## 4.2. InventoryModule
Отвечает за учёт остатков и складскую структуру.

Основные функции:

- получение остатков по товару;
- получение товаров в конкретной ячейке;
- увеличение остатка (при оприходовании);
- уменьшение остатка (при отгрузке);
- проверка достаточности остатка.
Пример состояний остатка:
```text
- InStock (В наличии)
- OutOfStock (Отсутствует)
- Reserved (Зарезервировано)
```

---

## 4.3. MovementModule
Отвечает за документооборот движения товаров.

Основные функции:

- создание документа прихода;
- создание документа расхода;
- проведение документа (связь с InventoryModule);
- отмена проведения документа;
- просмотр истории движений.
Модуль взаимодействует с:

```text
CatalogModule
InventoryModule
CounterpartyModule
```

---

## 4.4. CounterpartyModule

Отвечает за работу с контрагентами.

Основные функции:

- регистрация поставщика / покупателя;
- получение данных контрагента;
- изменение контактных данных.

# 5. Архитектурная схема

Для проекта выбрана модульная архитектура.
```text
                          ┌──────────────────┐
                          │      Клиент      │
                          └────────┬─────────┘
                                   │
                                   │ HTTP
                                   ▼
                          ┌──────────────────┐
                          │     ApiHost      │
                          │ ASP.NET Core API │
                          └────────┬─────────┘
                                   │
                  ┌────────────────┼─────────────────┐
                  │                │                 │
                  ▼                ▼                 ▼
         ┌────────────────┐ ┌───────────────┐ ┌────────────────┐
         │ MovementModule │ │CatalogModule  │ │InventoryModule │
         └───────┬────────┘ └───────────────┘ └───────▲────────┘
                 │                                     │
                 │ проверка товара                     │
                 └─────────────────────────────────────┘
                 │
                 │ изменение остатков
                 ▼
         ┌────────────────┐
         │InventoryModule │
         └────────────────┘
```

Центральным модулем бизнес-процесса является `MovementModule`.

При регистрации отгрузки он:

1. получает данные контрагента;
2. проверяет наличие товара в каталоге;
3. проверяет достаточность остатка;
4. создаёт документ движения;
5. уменьшает остаток в модуле учёта.

# 7. Внутренние зависимости

Внутренние зависимости определяют взаимодействие проектов внутри решения.

```text
Api
  ↓
 Movement
  ↓
 Contracts
 Api
  ↓
 Catalog
  ↓
 Contracts
 Api
  ↓
 Inventory
  ↓
 Contracts
 Api
  ↓
 Counterparties
  ↓
 Contracts
```

При этом бизнес-модули не должны напрямую обращаться к внутренним классам друг друга.

Взаимодействие выполняется через публичные контракты.

Например:

```text
MovementModule
      ↓
IStockUpdateService
      ↓
InventoryModule
```

Это позволяет уменьшить связанность модулей.

### 11.2. Назначение

Протокол используется при проведении документа поступления.

Асинхронный вызов через интерфейс C#:

```csharp

```

Зависимость передается через механизм Dependency Injection.

---

### 11.4. Точка входа

```csharp
Task<StockUpdateResult> AddStockAsync(
    AddStockRequest request,
    CancellationToken cancellationToken);
```

---

### 11.5. Формат запроса

```json
{
  "itemId": "8939af05-2a59-4758-a263-75df01c6d3f0",
  "warehouseId": "4f7fb20d-b92c-4082-a031-7eb643216a18",
  "quantity": 50.00,
  "movementDocumentId": "11223344-5566-7788-99aa-bbccddeeff00"
}
```

---

### 11.6. Успешный ответ

```json
{
  "success": true,
  "newBalance": 150.00,
  "errorCode": null
}
```

---

### 11.7. Ошибки

Возможные ошибки:

| Код | Описание |
| --- | --- |
| ITEM_NOT_FOUND | Товар не существует |
| WAREHOUSE_NOT_FOUND | Склад не существует |
| INVALID_QUANTITY | Количество меньше или равно нулю |

Операция должна завершиться не более чем за:

```text

```

---

### 11.9. Повторная отправка

Автоматический повтор не выполняется.

Повтор возможен только при ошибке таймаута, с проверкой статуса документа.

# 13. Общий сценарий создания документа расхода

После определения протоколов процесс отгрузки выглядит следующим образом:

```text
Клиент
   │
   │ Запрашивает отгрузку
   ▼
 ApiHost
   │
   ▼
 MovementModule
   │
   ├──────────────► CounterpartyModule
   │                 Проверка контрагента
   │
   ├──────────────► CatalogModule
   │                 Проверка существования товара
   │
   ├──────────────► InventoryModule
   │                 Проверка остатка и списание
   │
   │ Создание MovementDocument
   │
   └──────────────► (Сохранение в БД)
```

Результатом операции является проведённый документ расхода и уменьшенный остаток товара.

# 15. Тестовая стратегия

Для проекта предусматриваются два уровня проверки.

## 15.1. Модульные тесты

Модульные тесты должны проверять отдельные правила предметной области.

Примеры:

### Тест 1: 

Приход товара увеличивает остаток.

### Тест 2: 

Отгрузка при нулевом остатке возвращает `INSUFFICIENT_STOCK`.

### Тест 3: 

Отрицательное количество в запросе отклоняется (`INVALID_QUANTITY`).

### Тест 4: 

Отмена проведения документа расхода восстанавливает остаток.

## 15.2. Интеграционные тесты

Интеграционные тесты должны проверять взаимодействие модулей.


### Сценарий 1. 

```text
Успешная цепочка Приход -> Расход.
```

Ожидается: 

- остаток сначала увеличивается, затем уменьшается на корректную сумму.

### Сценарий 2. Параллельная отгрузка (Race condition).

Два запроса на отгрузку последних 2 единиц товара одновременно (по 2 единицы каждый).

Ожидается: 
- один запрос проходит, второй получает `INSUFFICIENT_STOCK`. 
- Остаток не уходит в минус.

## ADR-001. Использование модульной архитектуры

### Статус:

Принято.

### Проблема: 

Логика учёта остатков жёстко связана с документооборотом.

### Решение: 

Разделить на MovementModule (документы) и InventoryModule (остатки).

### Причина: 

Упрощает тестирование и позволяет в будущем добавить другие типы движений (например, внутреннее перемещение) без дублирования кода.

---

## ADR-002. Защита от отрицательных остатков

### Статус: 

Принято.

### Проблема: 

При параллельных запросах на отгрузку возможен уход остатка в минус.

### Решение: 

Использовать оптимистичные блокировки (Optimistic Concurrency) на уровне EF Core или транзакции с блокировкой записи (pessimistic) на уровне БД при списании.

### Последствия: 

Требует аккуратной обработки исключений при конфликтах (ConcurrencyException).

# 23. Оставшиеся риски

### Риск 1. Конкурентный доступ к остаткам (Race Condition).

Два кладовщика могут одновременно провести отгрузку одного товара.

Митигация: На этапе реализации внедрить механизмы блокировок на уровне БД.

### Риск 2. Ошибка проведения документа.

Документ может быть частично сохранён, а остаток не изменён.

Митигация: Использование транзакций (Unit of Work).

### Риск 3. Изменение справочников.

Удаление товара или склада, на котором есть остатки.

Митигация: Запрет на физическое удаление, использование "мягкого удаления" (soft delete).
